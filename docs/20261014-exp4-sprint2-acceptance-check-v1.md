## 两处确定的功能缺陷

### P2：旧身份探测与交互登录竞争

位置：`frontend/src/App.vue:69`，关联 `frontend/src/views/LoginView.vue:623`。

浏览器保留有效旧账号 Token，启动 `/auth/me` 尚未完成时从可见登录页提交新账号。若旧账号探测成功先返回、新登录后返回，旧探测将旧用户写入 App 并卸载登录页；新登录随后更新 Token，但页面不会收到已卸载组件的登录成功事件。

当前生产构建复现结果：新教师 Token 已存储，界面仍显示旧管理员，模板管理入口存在，新教师入口缺失；页面运行错误为 0。这是身份状态不一致，本轮未证明服务端越权。现有登录专项只覆盖另一种返回顺序，因此三组专项通过不能排除此缺陷。

证据：`20261013-exp4-sprint2-audit-v1/login-early/results.json`、`account-token-mismatch.png`、`login-early-success-diagnostic.cjs`。建议在交互登录开始时撤销/失效启动探测，并覆盖两种返回顺序的页面身份、角色入口与 Token 一致性。

### P2：迟到的启动加载覆盖历史大纲选择

位置：`frontend/src/views/TeacherDeskView.vue:897`、`:914`、`:955`、`:984`。

复现使用隔离真实后端，仅延迟启动阶段第一次排课请求的交付，不替换 API 内容。用户从初始班次切换到另一真实班次，打开指标矩阵并选择历史版本；随后放行原启动请求。

结果：放行前选中历史 ID 9，历史目标行存在；放行后选中当前 ID 10，历史目标行消失、当前目标行出现。原因是启动链路稍后才发起默认 `loadIndicators()`，它取得新的请求代次，现有“只采用最新请求”的保护允许其覆盖用户更晚的选择。

普通教师/主任历史切换四组专项均通过，但不能覆盖上述顺序。此问题影响 US-05 的版本追溯。建议给整个启动/班次加载链路增加用户选择上下文校验，确保迟到的默认加载不能改变后续历史选择，并保留此真实业务时序回归。

证据：`20261013-exp4-sprint2-audit-v1/history-startup-race/results.json`、`requests.json`、`history-overridden.png`。两个诊断脚本退出 0 表示成功复现错误行为，**不是对应业务验收通过**。
